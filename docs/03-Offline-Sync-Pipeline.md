# The Offline Synchronization Pipeline

Merian's core differentiator is treating Off-grid nature encounters as a first-class citizen using native Apple offline architecture.

## How the Queue Works

The `OfflineQueueManager` handles the persistence explicitly with no risk.

1. **Inference Failure & Queueing (`OfflineQueueManager.shared.enqueueCapture`)**
   When a hiker takes a picture miles away from a cell tower, the UI passes the raw capture and active context (like `gpsLatitude`, `gpsElevation`, `weatherCondition`, and `weatherTemperatureF`) to the `InferenceEngine`. To entirely prevent application storage block bloat on long off-grid excursions, the engine inherently detaches a compression loop mapping the 12MP buffer down into a highly compressed JPEG natively before any networking attempt. If `InferenceEngine` subsequentally encounters a `URLError` or network timeout natively interacting with the backend, it securely catches the failure and delegates the newly constrained payload instantly to `OfflineQueueManager.shared.enqueueCapture`. This compressed payload is locally written to the iOS `URL.documentsDirectory` and a new `OfflineQueuedScan` database object is written securely into the physical `.modelContainer()` using Apple `SwiftData`. Furthermore, if the user explicitly pushes the app into the background during a mid-flight active inference, `AppDIContainer` explicitly intercepts the native `.background` phase and rescues the payload. Critically, to prevent the 12MP uncompressed capture from leaking onto the user's hard drive, the AppDelegate boundary prioritizes extracting the `inferenceEngine.activeCompressedPayload` (the ~300KB downsampled footprint) first, completely protecting device storage. It also reads the active `gpsLatitude`, `gpsElevation`, `weatherCondition`, and `weatherTemperatureF` context parameters directly off the `InferenceEngine` state to ensure background-rescued scans preserve their complete physical dataset natively before suspending.

2. **Network Awakening (`NWPathMonitor`)**
   The `NWPathMonitor` instance listens natively to the internal cellular stack continuously. When a connection flips `.satisfied`, the manager debounces for 1,000 milliseconds to guarantee the pipeline has completely stabilized without thrashing before starting processing.

3. **Background Processing & Payload Compression (`URLSessionConfiguration.background`)**
   The manager checks that the queue isn't already syncing and securely verifies `!HardwareOrchestrator.shared.isExpeditionModeActive` to inherently prevent background cellular battery drain on low-power devices. It then bounds an explicitly constrained `FetchDescriptor` query with `descriptor.fetchLimit = 5` to chunk processing limits safely preventing edge timeout limits. It generates raw Presigned URLs from `/generate-upload-urls`.

   Critically, the core payload loop is securely initialized explicitly within a `Task.detached(priority: .background)` block, completely escaping the singleton's `@MainActor` confinement. However, because iterating the physical `PersistentModel` array offline forces Main Actor bounds, it explicitly maps the `pendingScans` data natively into purely standard thread-safe Tuple matrices (`let scanData = pendingScans.map...`) strictly prior to the detached `.background` hop, eliminating all `EXC_BAD_ACCESS` data race execution crashes. Inside this detached thread, the constrained `1:1` 1024x1024 geometric payload generated by `ImageCropperView` from `URL.documentsDirectory` is loaded, and downsampled recursively via a structurally `nonisolated` `CGImageSourceCreateThumbnailAtIndex` mapping with a `0.7` JPEG compression limit. Performing high-latency memory operations like native resizing strictly off the UI thread completely eliminates data race conditions preventing viewfinder freezing loops natively when heavy queues sync upon regaining cell connectivity. State interactions are cleanly routed back via safe `await MainActor.run` enclosures.

   This properly compressed payload is safely cached into a temporary `URL.cachesDirectory` file identified exactly by its unique `scanId` to strictly decouple and prevent asynchronous overwrite crashes natively. It is then cleanly handed directly into a strictly isolated native iOS `URLSession` Background Queue natively. The Operating System assumes full responsibility for byte transmission, massively accelerating upload times over spotty 3G cellular boundaries.
   _Note: A strict `UIBackgroundTaskIdentifier` map requests up to 30 seconds of explicit background execution time from iOS. An `expirationHandler` is wrapped locally around the presigned URL generation phase to immediately stop the queue loop, leaving remaining items safely in SwiftData without corrupting data if the OS randomly runs out of time on weak 3G connections. Crucially, it implements an expirationHandler closure to safely suspend the loop and call endBackgroundTask if the OS runs out of execution time, preventing data corruption and app crashes._

4. **Upload Lifecycle via URLSession Delegates (iOS Background Hooks)**
   - **Step A:** iOS natively transmits the data into the Staging bucket.
   - **Step B:** Once bytes finish landing securely, SwiftUI invokes the `@UIApplicationDelegateAdaptor` inside `AppDelegate`, transferring the `handleEventsForBackgroundURLSession` handler straight to `OfflineQueueManager`.
   - **Step C:** Native constraints fire `.urlSession(_:task:didCompleteWithError:)` triggering locally. The queue manager explicitly fetches the uploaded file via edge bounds (`MerianNetworkClient.shared.analyzeSubject`), retrieving the fully resolved JSON payload securely natively.
   - **Step D:** The returned taxonomy is passed securely to a dedicated `BackgroundDatabaseActor` where it decodes the payload, executes a strict `FileManager.default.copyItem()` hook duplicating the offline image boundaries exclusively preventing sandbox destruction natively entirely off the Main Thread. It then safely persists the fully identified creature explicitly into the user's `SwiftData` Life List. Finally, `processAndCleanupOfflineScan(scanId:)` automatically cleans up the old explicit queue references and raw duplicate media purely on its own background thread, completely insulating the 60FPS UI from stuttering during batch updates.

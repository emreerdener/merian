# Zero-OOM & Concurrency Architecture

Merian enforces a strict "Zero-OOM" (Out-Of-Memory), offline-first, and highly concurrent philosophy natively across its iOS client and serverless Deno Edge backend. This document captures the architectural decisions implemented to satisfy these demanding constraints.

## 1. iOS Concurrency & Memory Constraints (P0)

To fundamentally prevent UI hangs, memory leaks, and OS-level Watchdog terminations, the iOS app architecture imposes strict limits on resource boundaries:

### SwiftData Memory Exhaustion (`InsightSheetView`)
When querying records from massive user-generated biological libraries natively in SwiftData, executing a generic `FetchDescriptor` and filtering the `records.first(where:)` array synchronously in memory instantly triggers an OS JetSam out-of-memory crash for power users. Merian structurally prevents this array-loading catastrophe by natively injecting `#Predicate` constraints directly into the `FetchDescriptor`, forcing the underlying SQLite engine to isolate the single `targetId` perfectly without expanding V8 generic Swift collections.

### SwiftData Relationship Faults (OOM)
When managing many-to-many SwiftData relationships, mutating the "Many" side (e.g., `collection.scans.append(record)`) forces the underlying SQLite engine to synchronously fault the entire array (potentially thousands of heavy `LocalScanRecord` structures) into active RAM on the Main Thread. For power users, this guarantees an instantaneous JetSam Out-Of-Memory termination. To protect the RAM ceiling, explicit inverted "One" side mutation fixes were applied to `ScanCollection` in UI components like `ScanSelectionSheetView` and `CollectionDetailView`. Developers now explicitly mutate and read the "One" side of the relationship (e.g., `scan.collections?.append(collection)` and `scan.collections?.removeAll(...)`) rather than mutating the "Many" side (e.g., `collection.scans?.append(record)`) to prevent the SQLite engine from synchronously expanding massive data arrays into the V8 RAM footprint. Furthermore, deleting a collection explicitly bypasses iterative child array loops completely. By exclusively executing `modelContext.delete(collection)`, the system natively leverages SwiftData's default `.nullify` behavior, organically severing connections without pulling individual heavy payload bounds into active memory, permanently securing destructive operations against lethal JetSam crashes!

### SwiftUI View Invalidation Thrashing (`@Observable` Macro Migration)
Under the legacy `ObservableObject` protocol, whenever a core engine like `InferenceEngine` or `HardwareOrchestrator` mutated a background tracking array or hardware metric via `@Published`, it violently broadcast a global `objectWillChange` event. This forced SwiftUI to eagerly rip down and recalculate the `body` of every single view in the environment graph that injected the object natively (e.g., `CameraRootView`, `InsightSheetView`), even if those views only relied on isolated, unchanged properties like `isProcessing`. Merian strictly eliminated `ObservableObject` entirely from the codebase natively.
The architecture formally modernized all environmental managers (`AppDIContainer`, `CameraManager`, `HardwareOrchestrator`, `InferenceEngine`, and `ScansManager`) into physically bounded Swift 17+ `@Observable` classes natively. This radically drops the CPU render overhead natively because SwiftUI intrinsically tracks physical property access at runtime directly inside view closures. High-frequency background mutations (`subjectDistanceInMeters`) no longer thrash the global environment bounding, structurally preserving instantaneous 120Hz refresh rates and neutralizing severe thermal device loads reliably. Furthermore, all `@EnvironmentObject`, `@StateObject`, and `@ObservedObject` injections were meticulously stripped and remapped to modern `@Environment()`, `@State`, and `@Bindable` boundary constraints eliminating legacy view dependencies globally.

### SwiftUI 17 Environment Macros (`HapticManager`)
Historically, injecting singleton managers natively into the view hierarchy via `.environment(container.hapticManager)` that did *not* dynamically broadcast state (such as pure hardware execution wrappers containing no `@Published` or `@State` variables at all) compiled cleanly in older Swift iteratons. Merian strictly upgrades to iOS 18/Swift 6 toolchains. This modern architectural foundation enforces that *every* object passed natively into `.environment()` strictly evaluates as an `@Observable` macro instance, guaranteeing the SwiftUI engine uniformly tracks rendering graphs without opaque Class inheritance crashes. Classes like `HapticManager` implicitly adopt `@Observable` permanently despite lacking physical view bindings natively to cleanly satisfy the global AppDIContainer expansion boundaries flawlessly!

### SwiftUI Presentation Collisions (`CameraRootView`)
Apple's iOS 17 rendering engine violently throws fatal exceptions natively if a local UI attempts to instantiate multiple `.sheet` modifiers across concurrent background triggers (e.g. `isScansOpen = true` overlapping with `isInsightSheetOpen = true`). Merian strictly prevents UI presentation overlaps by entirely abandoning discrete `@Published` boolean switches in `CameraViewModel`. The navigation bounds strictly map against a single unified `enum ActiveSheet: Identifiable` property routed dynamically through a `Group { switch sheet }`. This inherently blocks the UI from issuing parallel presentation commands guaranteeing flawless 120Hz view bouncing without iOS framework layer crashes.

### Swift 6 MainActor Initialization (`CaptureTelemetry`)
When mapping telemetry datasets natively from the global `InferenceEngine` explicitly over into a lightweight, `Sendable` `CaptureTelemetry` construct for network offloading, utilizing a standard struct initializer `init(from inferenceEngine:)` implicitly violates strict Swift 6 concurrency maps. Because the `InferenceEngine` tracks its properties exclusively on the `@MainActor` thread, a non-isolated initializer technically attempts to cross bounded execution states triggering a fatal "Main actor-isolated property can not be referenced from a nonisolated context" compiler lockout. Merian fundamentally abandons generic initialization closures here, natively tagging `@MainActor` explicitly atop the `CaptureTelemetry` initialization bound itself (`@MainActor init(from inferenceEngine: InferenceEngine)`), mathematically validating the execution tree identically aligns directly with `AppDIContainer.handleBackgroundPhase()` naturally executing on the UI Thread.

### SwiftData Environment Tearing (`MerianApp`)
Attaching `.modelContainer(container)` strictly to conditional child elements (like `.modelContainer` embedded dynamically on `CameraRootView` but not `OnboardingView` inside an `if/else` block) forces iOS to entirely tear down and logically rebuild the massive SwiftData mapping environment natively during runtime view swaps. This inherently creates catastrophic layout passes resulting in blank screens or crashed queries. Merian strictly hoists all heavy `@Environment` injectables explicitly over the outer conditional `Group` shell, ensuring the database mounts flawlessly from frame-zero unconditionally.

### Eager Hardware Instantiation (`CameraManager` & `PhotoLibraryManager`)
Globally instantiating underlying hardware layers (such as dynamically wiring `AVCaptureDeviceInput` exclusively inside `CameraManager.init()`) is explicitly prohibited. Because Merian leverages `AppDIContainer.shared` scaling managers efficiently down the structural tree natively via `.environmentObject`, these classes boot fully instantly on cold launch. Executing native Apple hardware configuration physically inside an `init` systematically defeats the entire Onboarding UI Permission Priming pipeline natively, popping stark system API Modals completely out of bounds (such as the OS jumping the `WelcomeStepView` natively for camera limits!). The architecture structurally bounds hardware instantiation by enforcing deferred execution boundaries—massive locks like `.setupSession()` or `PHPhotoLibrary.requestAuthorization` are formally shifted completely out to explicit `.startSession()` invocation blocks securely orchestrating OS bindings physically behind UX limits.

### Lifecycle Initialization Leaks (`AppDIContainer`)
On a fresh application cold-boot, SwiftUI inherently evaluates the global `WindowGroup` environment and transitions the `Environment(\.scenePhase)` from `.inactive` seamlessly to `.active`. `MerianApp` implicitly observes this global trigger and executes unified "wake-up" loops inside `AppDIContainer.handleActivePhase()` (such as bootstrapping `cameraManager.startSession()` and syncing offline inference records). Because this iOS lifecycle hook fires sequentially milliseconds *before* the first `OnboardingView` explicitly paints, it completely bypassed Onboarding gating natively, forcibly initializing the camera layer and instantly spawning the OS API permission alert immediately atop the first Onboarding UI slice natively! To rigorously enforce bounded onboarding states, `AppDIContainer` state transitions strictly evaluate `UserDefaults.standard.bool(forKey: "hasCompletedOnboarding")` inline, aggressively aborting all hardware pings, sync requests, and background evaluations completely until the user finishes the literal onboarding sequence natively.

### SwiftUI Render Loop CPU Thrashing (`ScansThumbnailView`)
When loading Grid arrays parsing `SwiftData` entries, missing `imagePath` and `fallbackImageUrl` matrices previously mapped conditionally to `.task(id: ... ?? UUID().uuidString)`. SwiftUI natively invalidates running async `.task { }` executions exactly whenever their tracked `id` parameter fundamentally alters. By returning a dynamic UUID inline, SwiftUI intrinsically aborted the task, forced a view invalidation, executed the layout dynamically, and evaluated a *brand new UUID* seamlessly re-triggering the task recursively. This created infinite continuous cancellation loops executing relentlessly at 120Hz locally, generating 100% Core Load allocations entirely consuming device battery natively. Merian intrinsically bypasses rendering hazards cleanly simply replacing logical UUID generation boundaries with constant literal bound evaluations natively via `?? "empty_thumbnail_state"`.

### SQLite Thread-Safety Violations (`ArchiveManager`)
Instantiating non-isolated `ModelContext` containers directly inside arbitrary `Task.detached` background closures explicitly violates strict Swift 6 concurrency parameters, generating rampant data races and `EXC_BAD_ACCESS` fatal crashes natively under massive load. Merian explicitly abandons arbitrary detached SQLite threading; it maps background database ingestion (such as rescuing aging `.jpg` blobs off the S3 proxy) strictly inside localized `@ModelActor` constructs (like `ArchiveDatabaseActor`). This structurally isolates the SQL read/write matrix cleanly inside a sequential concurrent thread pool inherently preventing memory access corruption. Furthermore, duplicated structural object mapping logic across models (such as copying 40-line `SpeciesData` initialization dictionaries implicitly inside `OfflineQueueManager`) is aggressively consolidated securely back into their `init(fromEdgeResponse:)` origins cleanly isolating network JSON execution boundaries preventing data parity errors securely.

### Background Suspension Limits (`OfflineQueueManager`)
When evaluating inference payloads in the wilderness disconnected from cell service, the system natively requires `UIBackgroundTaskIdentifier` hooks to complete URLSession executions. In `Merian`, these handles are explicitly extracted *outside* of generic `@MainActor` task executions to defeat rapid synchronous delegate fire-and-return OS suspension traps natively. 
We employ unified generic `BackgroundTaskWrapper` reference boxes secured with `NSLock` instances to seamlessly bind these background identifiers. To strictly eliminate duplicated `#if os(iOS)` preprocessor macros and `endBackgroundTask` loops across `enqueueCapture`, `syncPendingScans`, and background URLSessions, the architecture invokes a unified static execution abstraction natively: `BackgroundTaskWrapper.execute(name:operation:)`. This rigid generic boundary exclusively handles registering the active memory environment, securely tracking the OS expiration fallback closures, and perfectly invoking `.endBackgroundTask` inside an implicit `defer` block safely guaranteeing `URLSession` callbacks seamlessly execute over thread boundaries out of the core user grid logic safely.
If a user hits the physical capture button and immediately locks their phone before the NVMe controller finishes writing `.jpg` bytes cleanly to disk natively, iOS instantly violently suspends the thread, permanently generating a corrupted 0KB binary footprint. By explicitly wrapping the disk I/O parameter inside this rigorous OS Background limit hook, Merian natively commands the iOS SpringBoard to grant the exact millisecond differential required to cleanly flush the data buffer preventing payload corruption.
Crucially, when bridging these strict Swift 6 concurrency boundaries via `Task.detached`, Merian inherently injects these reference boxes as Sendable captures perfectly tracking temporal OS states locally. By dropping optional limits cleanly natively processing `.invalid` locks dynamically over the abstraction limits, the system strictly eliminates iOS Watchdog panics permanently natively!
Furthermore, to structurally prevent iOS from violently suspending the application natively before background I/O queues successfully tear down, Merian strictly abolishes invoking detached `Task { ... }` blocks orphaned inside asynchronous `defer` closures. Inside the `URLSession` completion handler natively, active task evaluations (`session.allTasks`) are rigorously executed directly within the synchronous, awaited boundary of the `BackgroundTaskWrapper.execute` mapping, definitively guaranteeing the queue lock releases successfully before the `UIBackgroundTaskIdentifier` expires natively.
Furthermore, to prevent Swift 6 Sendable reference structural violations natively, `urlSession(_:task:didCompleteWithError:)` extracts non-Sendable `task.taskDescription` and HTTP string properties into local immutable variables directly on the delegate context seamlessly prior to traversing back across the background wrapper boundary dynamically!
Additionally, early function return closures in `OfflineQueueManager` skipping inference (due to `504` error codes natively) unintentionally skipped `SyncStateManager.shared.completeSync()`. This permanently deadlocked the offline queue natively. Merian strictly bounds these teardowns natively leveraging a block `defer` dynamically checking if `session.allTasks.isEmpty` securely running the teardowns unconditionally natively overriding all possible abort paths inherently preventing deadlocks.
Furthermore, when chunking pending offline scans to the Edge Function payload boundary, Merian mathematically caps loop payloads cleanly via `.prefix(5)` on the `filteredScans` array. Previously, dynamically enforcing a secondary `.prefix(5)` limit strictly against the flattened `fileNames`, `fileURLs`, and `scanIDs` arrays inadvertently severed multi-image payloads (since one offline scan now bounds up to 2 local images). By completely removing the truncation on the flattened arrays and relying solely on the scan-level limit, the architecture guarantees a partial payload state is never pushed to Cloudflare R2, preventing silent infinite `HTTP 400 Array Length exceptions` while preserving data integrity.
	
### Background Delegate Deadlocks (`PushNotificationManager`)
When executing `URLSession` hooks off-grid directly via a background task identifier, the Merian Application strictly remains visually suspended but structurally executing via an `active` physical process. When AI processing triggered completion alerts, `UNUserNotificationCenterDelegate` natively fired `willPresent` because the process was alive! ### Double-Rotation EXIF Artifacts (`CameraManager`)

### Hanging Continuations (`CameraManager`)
Apple's ISP (Image Signal Processor) can stall during extreme thermal saturation, failing to return an image frame via `AVCapturePhotoCaptureDelegate`. Rather than silently hanging the `isShutterActive` UI state indefinitely, Merian wraps structural `withCheckedThrowingContinuation` patterns securely inside a `withTaskCancellationHandler`. Critically, to safely orchestrate multiple overlapping captures natively on a single UI state, Merian dynamically associates a generic array tracking queue (`activeCaptureRequests`) cleanly isolating concurrent `timeoutTask?.cancel()` closures explicitly mapped through unique UUID identifiers, instantly wiping specific stalling arrays out of RAM while resolving any dropped continuations securely via standard `CancellationError` triggers without locking subsequent successful snaps.

### Thread Starvation & Dropped Frames (`InferenceEngine`)
To prevent the Main Thread from stuttering during extreme native Swift UI interactions (like 120Hz `ScrollView` dragging), Merian prohibits standard Main Actor `JSONDecoder()` operations against massive scientific dictionary responses. Instead, the structural decoding is entirely detoured into `Task.detached(priority: .userInitiated)`. Crucially, to prevent Swift 6 concurrency race conditions generating `EXC_BAD_ACCESS` memory corruption during rapid multi-threading boundaries natively, SwiftData `.insert()` ingestion is explicitly decoupled out of the raw `.detached` payload and routed directly through the `@ModelActor BackgroundDatabaseActor`, cleanly preserving isolated SQL boundaries natively. 
If the user rapidly mashes the capture shutter, old execution loops are explicitly aborted via `self.inferenceTask?.cancel()` at the very top of `.analyze()`, immediately severing orphan tasks that leak memory, draw excess cellular data, and improperly increment hard API limits natively.
Additionally, when checking historic scans natively, local `FileManager` checks determining sandbox paths are strictly prevented from binding into the `InsightCarousel` rendering engine. They natively evaluate asynchronously within `InferenceEngine` dynamically binding to `@Published` values guaranteeing flawless 60fps Carousel snapping.

### Main Thread Disk I/O Blocking
Executing local `FileManager` disk sweeps and `URLSession` network downloads synchronously on the `@MainActor` thread violently locks the 120Hz UI refresh rate during heavy executions. In Merian, functions like `saveUserPhotos()` inside `InsightMediaExportManager` and massive local cache clearance loops in the User Profile are completely and explicitly decoupled into `Task.detached(priority: .userInitiated)` and `Task.detached(priority: .utility)` blocks. ### OOM-Safe Bulk Eradication (`NonBiologicalScansView`)

# Zero-OOM & Concurrency Architecture

Merian enforces a strict "Zero-OOM" (Out-Of-Memory), offline-first, and highly concurrent philosophy natively across its iOS client and serverless Deno Edge backend. This document captures the architectural decisions implemented to satisfy these demanding constraints.

## 1. iOS Concurrency & Memory Constraints (P0)

To fundamentally prevent UI hangs, memory leaks, and OS-level Watchdog terminations, the iOS app architecture imposes strict limits on resource boundaries:

### SwiftData Memory Exhaustion (`InsightSheetView`)
When querying records from massive user-generated biological libraries natively in SwiftData, executing a generic `FetchDescriptor` and filtering the `records.first(where:)` array synchronously in memory instantly triggers an OS JetSam out-of-memory crash for power users. Merian structurally prevents this array-loading catastrophe by natively injecting `#Predicate` constraints directly into the `FetchDescriptor`, forcing the underlying SQLite engine to isolate the single `targetId` perfectly without expanding V8 generic Swift collections.

### SwiftData Relationship Faults (OOM)
When managing many-to-many SwiftData relationships, mutating the "Many" side (e.g., `collection.scans.append(record)`) forces the underlying SQLite engine to synchronously fault the entire array (potentially thousands of heavy `LocalScanRecord` structures) into active RAM on the Main Thread. For power users, this guarantees an instantaneous JetSam Out-Of-Memory termination. To protect the RAM ceiling, explicit inverted "One" side mutation fixes were applied to `ScanCollection` in UI components like `ScanSelectionSheetView` and `CollectionDetailView`. Developers now explicitly mutate and read the "One" side of the relationship (e.g., `scan.collections?.append(collection)` and `scan.collections?.removeAll(...)`) rather than mutating the "Many" side (e.g., `collection.scans?.append(record)`) to prevent the SQLite engine from synchronously expanding massive data arrays into the V8 RAM footprint.

### SwiftUI Presentation Collisions (`CameraRootView`)
Apple's iOS 17 rendering engine violently throws fatal exceptions natively if a local UI attempts to instantiate multiple `.sheet` modifiers across concurrent background triggers (e.g. `isScansOpen = true` overlapping with `isInsightSheetOpen = true`). Merian strictly prevents UI presentation overlaps by entirely abandoning discrete `@Published` boolean switches in `CameraViewModel`. The navigation bounds strictly map against a single unified `enum ActiveSheet: Identifiable` property routed dynamically through a `Group { switch sheet }`. This inherently blocks the UI from issuing parallel presentation commands guaranteeing flawless 120Hz view bouncing without iOS framework layer crashes.

### SwiftUI Zero-Frame Animation Collapse (`UIViewRepresentable`)
When dynamically swapping massive `UIViewRepresentable` camera bounds natively (e.g. tearing down `OnboardingView` and spawning `CameraRootView` via an `@AppStorage` flag), executing the Boolean flip inside an explicit `withAnimation` block forces the SwiftUI engine to intrinsically animate the entire `CameraPreviewView` insertion into the DOM. Natively, this causes the underlying `AVCaptureVideoPreviewLayer` to evaluating its geometric frame as size `(0,0)` during the active transition, permanently stranding the entire layout grid, ripping UI interfaces off-screen, and painting massive blank `NavigationStack` backgrounds. Merian strictly outlaws `withAnimation` blocks when dynamically hot-swapping heavy hardware view wrappers at the root, generating a perfect, instantaneous flush replacement natively.

### SwiftData Environment Tearing (`MerianApp`)
Attaching `.modelContainer(container)` strictly to conditional child elements (like `.modelContainer` embedded dynamically on `CameraRootView` but not `OnboardingView` inside an `if/else` block) forces iOS to entirely tear down and logically rebuild the massive SwiftData mapping environment natively during runtime view swaps. This inherently creates catastrophic layout passes resulting in blank screens or crashed queries. Merian strictly hoists all heavy `@Environment` injectables explicitly over the outer conditional `Group` shell, ensuring the database mounts flawlessly from frame-zero unconditionally.

### Eager Hardware Instantiation (`CameraManager` & `PhotoLibraryManager`)
Globally instantiating underlying hardware layers (such as dynamically wiring `AVCaptureDeviceInput` exclusively inside `CameraManager.init()`) is explicitly prohibited. Because Merian leverages `AppDIContainer.shared` scaling managers efficiently down the structural tree natively via `.environmentObject`, these classes boot fully instantly on cold launch. Executing native Apple hardware configuration physically inside an `init` systematically defeats the entire Onboarding UI Permission Priming pipeline natively, popping stark system API Modals completely out of bounds (such as the OS jumping the `WelcomeStepView` natively for camera limits!). The architecture structurally bounds hardware instantiation by enforcing deferred execution boundaries—massive locks like `.setupSession()` or `PHPhotoLibrary.requestAuthorization` are formally shifted completely out to explicit `.startSession()` invocation blocks securely orchestrating OS bindings physically behind UX limits.

### Lifecycle Initialization Leaks (`AppDIContainer`)
On a fresh application cold-boot, SwiftUI inherently evaluates the global `WindowGroup` environment and transitions the `Environment(\.scenePhase)` from `.inactive` seamlessly to `.active`. `MerianApp` implicitly observes this global trigger and executes unified "wake-up" loops inside `AppDIContainer.handleActivePhase()` (such as bootstrapping `cameraManager.startSession()` and syncing offline inference records). Because this iOS lifecycle hook fires sequentially milliseconds *before* the first `OnboardingView` explicitly paints, it completely bypassed Onboarding gating natively, forcibly initializing the camera layer and instantly spawning the OS API permission alert immediately atop the first Onboarding UI slice natively! To rigorously enforce bounded onboarding states, `AppDIContainer` state transitions strictly evaluate `UserDefaults.standard.bool(forKey: "hasCompletedOnboarding")` inline, aggressively aborting all hardware pings, sync requests, and background evaluations completely until the user finishes the literal onboarding sequence natively.

### SwiftUI Render Loop CPU Thrashing (`ScansThumbnailView`)
When loading Grid arrays parsing `SwiftData` entries, missing `imagePath` and `fallbackImageUrl` matrices previously mapped conditionally to `.task(id: ... ?? UUID().uuidString)`. SwiftUI natively invalidates running async `.task { }` executions exactly whenever their tracked `id` parameter fundamentally alters. Merian intrinsically bypasses rendering hazards cleanly simply replacing logical UUID generation boundaries with constant literal bound evaluations natively via `?? "empty_thumbnail_state"`.

### SQLite Thread-Safety Violations (`ArchiveManager`)
Instantiating non-isolated `ModelContext` containers directly inside arbitrary `Task.detached` background closures explicitly violates strict Swift 6 concurrency parameters, generating rampant data races and `EXC_BAD_ACCESS` fatal crashes natively under massive load. Merian explicitly abandons arbitrary detached SQLite threading; it maps background database ingestion (such as rescuing aging `.jpg` blobs off the S3 proxy) strictly inside localized `@ModelActor` constructs (like `ArchiveDatabaseActor`). This structurally isolates the SQL read/write matrix cleanly inside a sequential concurrent thread pool inherently preventing memory access corruption. Furthermore, duplicated structural object mapping logic across models (such as copying 40-line `SpeciesData` initialization dictionaries implicitly inside `OfflineQueueManager`) is aggressively consolidated securely back into their `init(fromEdgeResponse:)` origins cleanly isolating network JSON execution boundaries preventing data parity errors securely.

### Background Suspension Limits (`OfflineQueueManager`)
When evaluating inference payloads in the wilderness disconnected from cell service, the system natively requires `UIBackgroundTaskIdentifier` hooks to complete URLSession executions. This rigid generic boundary exclusively handles registering the active memory environment, securely tracking the OS expiration fallback closures, and perfectly invoking `.endBackgroundTask` inside an implicit `defer` block safely guaranteeing `URLSession` callbacks seamlessly execute over thread boundaries out of the core user grid logic safely.
If a user hits the physical capture button and immediately locks their phone before the NVMe controller finishes writing `.jpg` bytes cleanly to disk natively, iOS instantly violently suspends the thread, permanently generating a corrupted 0KB binary footprint. By explicitly wrapping the disk I/O parameter inside this rigorous OS Background limit hook, Merian natively commands the iOS SpringBoard to grant the exact millisecond differential required to cleanly flush the data buffer preventing payload corruption.

By dropping optional limits cleanly natively processing `.invalid` locks dynamically over the abstraction limits, the system strictly eliminates iOS Watchdog panics permanently natively!

### Hanging Continuations (`CameraManager`)
Apple's ISP (Image Signal Processor) can stall during extreme thermal saturation, failing to return an image frame via `AVCapturePhotoCaptureDelegate`. Rather than silently hanging the `isShutterActive` UI state indefinitely, Merian wraps structural `withCheckedThrowingContinuation` patterns securely inside a `withTaskCancellationHandler`. ### Thread Starvation & Dropped Frames (`InferenceEngine`)
To prevent the Main Thread from stuttering during extreme native Swift UI interactions (like 120Hz `ScrollView` dragging), Merian prohibits standard Main Actor `JSONDecoder()` operations against massive scientific dictionary responses. Instead, the structural decoding is entirely detoured into `Task.detached(priority: .userInitiated)`. Crucially, to prevent Swift 6 concurrency race conditions generating `EXC_BAD_ACCESS` memory corruption during rapid multi-threading boundaries natively, SwiftData `.insert()` ingestion is explicitly decoupled out of the raw `.detached` payload and routed directly through the `@ModelActor BackgroundDatabaseActor`, cleanly preserving isolated SQL boundaries natively.

### Main Thread Disk I/O Blocking
Executing local `FileManager` disk sweeps and `URLSession` network downloads synchronously on the `@MainActor` thread violently locks the 120Hz UI refresh rate during heavy executions. In Merian, functions like `saveUserPhotos()` inside `InsightMediaExportManager` and massive local cache clearance loops in the User Profile are completely and explicitly decoupled into `Task.detached(priority: .userInitiated)` and `Task.detached(priority: .utility)` blocks. ### SwiftUI Task Cancellation Swallowing
When generating dynamic delays (like `toastMessage` banners) using SwiftUI's native `.task(id:)` modifier, utilizing `try? await Task.sleep()` fatally swallows the native `CancellationError` payload. If the `id` changes rapidly, the swallowed error prevents the active task from aborting correctly, creating race conditions where multiple toast timers overlap and prematurely clear the UI state. Merian enforces strictly executing `try await Task.sleep()` without the optional coalescing inside bounding `.task(id:)` structures (e.g., fixing `InsightSheetView` toast races) to guarantee SwiftUI cancels previous suspended timers instantly.

### UI Thread Blocking (`SettingsView` Exports)
Generating a global Darwin Core Archive (DwC-A) over the `/export-dwca` Edge node forces native HTTP barriers to hold connections open for over 100+ seconds depending on user library sizing constraints natively. Emitting this asynchronous hook directly on the `@MainActor` thread would trigger severe scrolling stutters or complete Watchdog terminations. 
The `MerianNetworkClient.shared.exportDwcA` task is explicitly hoisted away from the UI into an isolated `Task.detached(priority: .userInitiated)` shell seamlessly toggling an insulated `@MainActor` `isExporting` state. Behind this bounded boundary, a dedicated `@ModelActor SearchDatabaseActor` perfectly isolates execution loops. It structurally abandons unbounded `FetchDescriptor` bulk mapping natively which previously forced the entire database to expand into a RAM dictionary precipitating JetSam OS terminations for extreme 5,000+ capacity users natively. Instead, it systematically iterates through the localized ID array, leveraging the ultra-efficient `model(for: id)` hook to fault specific database payloads natively into memory progressively, structurally preserving an exact O(1) resolution trace safely without violating core memory limits. It perfectly transforms the discrete arrays into `SearchableScan` structures securely, explicitly calling `await MainActor.run` natively ONLY when the search cache finishes securely mapping the query strings in the background. Furthermore, to prevent CPU thrashing (100% CPU utilization) during rapid typing sequences, the detached sequence is bound to an explicit `indexingTask` reference; earlier task executions are successfully terminated instantly via `indexingTask?.cancel()` checking dynamic `Task.isCancelled` states shedding redundant payload string execution.

### UI Body Array Calculations (`UserProfileStatsView`)
When executing heavy `O(N)` structural array manipulations (such as `Set(allRecords.map { ... }).count` or `Calendar` sorting logic) directly inside a SwiftUI `var body: some View`, any update triggered by global `@Query` bindings forces the Main Thread to re-evaluate the entire math loop synchronously. ## 2. Deno Edge Scalability & OOM Protection (P1)

Deno Edge functions run in an ultra-restricted 256MB V8 heap footprint. To handle scale gracefully without 504 Timeouts:

### Explicit Buffer Resolving vs Chunked Streams (`export-dwca`)
Global researchers pulling thousands of scientific records previously crashed AWS V4 Signatures on Cloudflare R2 when piping `<ReadableStream>` duplexes because the edge router dynamically appended `Transfer-Encoding: chunked` headers, eliciting violent `411 Length Required` or `403 Signature Does Not Match` rejections. Since actual physical images are deliberately offloaded from the .zip payload, the `export-dwca` generator natively limits its size under 10MB statically. Merian abandons streaming completely here, explicitly commanding `await zip.generateAsync({ type: "uint8array" })` to calculate the exact `Content-Length` binary bound natively bypassing AWS generic stream rejections without violating the 256MB V8 RAM limits.
Crucially, when sequentially mapping 50,000+ payload columns natively off the PostgreSQL database, executing `+=` string concatenations dynamically inside the `while(hasMore)` loop aggressively demanded massive reallocation of contiguous memory blocks, triggering O(N^2) memory fragmentation that rapidly blew out the container V8 256MB bounds resulting in massive execution restarts. The edge routing explicitly replaced string concatenations organically utilizing `.push()` inside native JS arrays. It executes a single `.join("\n")` computation instantaneously before the `JSZip` injection cleanly ensuring the Deno engine actively scales its memory trace seamlessly.

### Direct Base64 Network Offloading (`identify`)
Merian explicitly bypasses executing traditional asynchronous `.arrayBuffer()` extractions off external S3 physical boundaries wherever possible. To completely circumvent V8 memory loading cycles pulling geometric payloads from Cloudflare across HTTP lines, iOS translates the `140KB` payload natively into a literal `"imageBase64": "..."` string directly inside the payload map. This mathematically maps the geometric data organically within the 256MB functional bound natively skipping the S3 staging download entirely and returning an ultra-fast response securely!

### Vector Sizing Attacks (`identify`)
Merian strictly protects backend endpoints from malformed or malicious multi-gigabyte S3 object structures by natively extracting `r2Response.headers.get("Content-Length")`. Any object exceeding the `5MB` constraint gracefully yields an `HTTP 413 Payload Too Large` immediately before the backend `.arrayBuffer()` parser attempts to evaluate it natively preventing Deno restarts.

### V8 Event Loop Saturation (`export-dwca`)
Generating Darwin Core Archives natively extracts tens of thousands of occurrences securely masking global user identities via `crypto.subtle.digest` logic. Constructing a monolithic asynchronous mapping `Promise.all(scans.map(...)` array completely halts the Deno V8 Javascript event loop, blocking HTTP threads, starving the Node container, and producing lethal `504 Gateway Timeout` errors natively. Merian rigidly forces the loop into an isolated chunking matrix explicitly pushing blocks sequentially into the stack preserving deep backend thread latency and stopping CPU threshold limit exhaustion dead in its tracks. Additionally, to avoid data loss on massive global archives, `.limit(5000)` truncations were eradicated replacing the query matrix with an explicit `while(hasMore)` loop utilizing cursor-based `.range(start, start + PAGE_SIZE - 1)` bounds. Crucially, the system abandons caching raw `scans` payloads into a global array. It dynamically stringifies each Postgres dictionary chunk back natively into the `.csv` iteration arrays, explicitly allowing the massive upstream JSON geometries to be violently GC'd (Garbage Collected) by V8 instantly, securely circumventing lethal 256MB Out-Of-Memory edge container panics.

### Native Execution Deferrals (`revenuecat-webhook`)
S3 bulk-bucket mutations (e.g. migrating 1000s of payloads from `/free/` into `/pro/` prefixes) exceeded Deno's 10-second processing restriction for power users. Merian decouples the webhook execution by logging tier upgrades and issuing `HTTP 200` instantly, natively deferring all structural S3 R2 operations cleanly out to the background via `EdgeRuntime.waitUntil(promise)`. Crucially, to prevent massive V8 memory consumption and wall-clock sequential timeouts inside the detached operation natively, the mapping executes over a `Promise.allSettled` block chunked explicitly into bounding matrices of `BATCH_SIZE = 50`. Furthermore, to prevent lethal AWS V4 Signature `403 Forbidden` API crashes on user payloads containing spaces, the `x-amz-copy-source` header is structurally wrapped firmly within `encodeURI()`.

## 3. Infrastructure Latency & Privacy (P2)

### O(N) Main Thread UI Starvation (`ScansSearchManager`)
